# Fine-Tuning LLMs for Self-Refining Reasoning

Can a small language model learn to **check its own work**? This project fine-tunes small Qwen3.5 base models (2B and 4B) to write two attempts at a math problem, **review** them, and then give a final answer. The self-refining model is compared with the untouched base model and with conventional chain-of-thought (CoT) fine-tuning on the MATH-500 benchmark, using the same problems, the same compute and significance tests. The trained models can be tried in a chat website.

**Live demo:** https://finetuning-ochre.vercel.app (the GPU servers run on Kaggle and are switched on for demos; when they are off the site says "GPU offline")

**Headline result (Qwen3.5-4B-Base, MATH-500):**

| Model | Accuracy |
|---|---|
| Base model | 68.2% |
| CoT fine-tuning (conventional reasoning) | 71.6% |
| **Self-refine fine-tuning (ours)** | **75.4%** |

Self-refinement beats both the base model (p = 0.0002) and CoT fine-tuning (p = 0.048, McNemar test). When its two attempts disagree and only one is right, the model picks the right one **83%** of the time.

---

## 1. Problem statement

> Fine-tune a pretrained language model to generate multiple reasoning chains, reconsider its initial approach, and produce a more refined final answer. Evaluate the improvement in reasoning performance and demonstrate the difference between conventional and self-refining reasoning.

Language models usually answer in one pass: whatever the first chain of reasoning says is the answer. Small models make many mistakes this way, and simply asking a model to "check your answer" often does not help, because it cannot tell its right answers from its wrong ones. This project asks whether that ability can be **trained in**: if a small model sees many examples of "two attempts, a review that finds the mistake, and the corrected answer", does it learn to actually reconsider?

## 2. What the model learns to write

Every training example (and every answer at test time) has this shape:

```
[Question] A math problem
[Answer 1] first attempt, step by step ... \boxed{...}
[Answer 2] second attempt, step by step ... \boxed{...}
[Review] short critique: which attempt is right, and the exact step where the other goes wrong
[Final answer] ...
```

The two attempts are the model's **own** attempts (generated by the same base model before training), so it learns to critique the kind of mistakes it really makes.

## 3. Method

| Step | What happens | Notebook |
|---|---|---|
| 1. Baseline | Run the untouched base model on MATH-500 | `01_baseline_math500` |
| 2. Attempts | For each of ~7,500 MATH training problems (MATH-500 removed), the base model writes 4 attempts; each is graded with `math_verify` | `02_generate_chains` |
| 3. Pairs | Pick two attempts per problem: **correction** (wrong then right), **keep** (right then wrong) and **agree** (both right) | `03_select_pairs`, `03_select_pairs_4b` |
| 4. Reviews | A larger **teacher** model reads both attempts (and the known correct answer) and writes the review in the student's voice. Reviews are kept only if they end in the correct answer and never mention being told the answer | `04_generate_reviews` (Qwen3.5-9B), `04b_generate_reviews_qwen27b` (Qwen3.8-27B) |
| 5. Training files | Three versions on the **same problems**: Review (method), Refine (ablation: rewrite the whole solution instead of reviewing) and CoT (baseline: one correct chain) | `05_build_sft_data`, `05b_build_sft_data_27b`, `05_build_sft_data_4b` |
| 6. Fine-tuning | LoRA fine-tuning with TRL `SFTTrainer`; loss only on the answer part | `06_train_sft` |
| 7. Evaluation | Merge the adapter, generate on MATH-500 with vLLM (greedy), grade with `math_verify` | `07_evaluate` |
| 8. Analysis | Tables, self-correction metrics, McNemar significance tests, examples | `08_results_analysis` |
| 9. Inference | Serve the trained models to the chat website | `09_inference_server` |

**Training settings:** LoRA r=16, alpha=32 on attention, linear-attention and MLP projections; learning rate 1e-4 (cosine); 2 epochs; batch 1 x 16 gradient accumulation; max length 2048; completion-only loss. 2B trained in float32 weights with fp16 mixed precision; 4B in float16 weights (to fit on one T4).

**Evaluation settings:** MATH-500, greedy decoding, up to 3072 new tokens, `repetition_penalty=1.1`, answers graded with `math_verify`.

**Compute:** everything ran on free Kaggle GPUs (2x NVIDIA T4). The 27B teacher ran in 4-bit (GPTQ) across both T4s.

## 4. Results

### 4.1 Qwen3.5-2B-Base

| Model | Accuracy | Final answer vs first attempt | Picked right attempt* |
|---|---|---|---|
| Base 2B | 55.6% | - | - |
| CoT fine-tuning | 57.4% | - | - |
| Refine (rewrite the solution) | 54.6% | -2.2 | 65.4% |
| Review, 9B teacher | 59.8% | +2.4 | 71.3% |
| **Review, 27B teacher** | **61.2%** | **+3.8** | **76.6%** |

### 4.2 Qwen3.5-4B-Base

| Model | Accuracy | Final answer vs first attempt | Picked right attempt* |
|---|---|---|---|
| Base 4B | 68.2% | - | - |
| CoT fine-tuning | 71.6% | - | - |
| **Review, 27B teacher** | **75.4%** | **+7.2** | **83.1%** |

\* When the two attempts disagree and exactly one is right, how often the final answer is the right one. Guessing would give 50%.

### 4.3 Significance (McNemar test on the 500 problems)

| Comparison | p-value | Significant (p < 0.05)? |
|---|---|---|
| 4B Review vs 4B Base | 0.0002 | Yes |
| **4B Review vs 4B CoT** | **0.048** | **Yes** |
| 4B CoT vs 4B Base | 0.078 | No |
| 2B Review (27B) vs 2B Base | 0.009 | Yes |
| 2B Review (27B) vs 2B Refine | 0.002 | Yes |
| 2B Review (27B) vs 2B CoT | 0.079 | No |
| 2B Review (27B) vs 2B Review (9B) | 0.53 | No |

### 4.4 Accuracy by difficulty (4B)

| Model | Level 1 | Level 2 | Level 3 | Level 4 | Level 5 |
|---|---|---|---|---|---|
| Base 4B | 86.0 | 87.8 | 82.9 | 68.0 | 38.1 |
| CoT 4B | 97.7 | 88.9 | 82.9 | 71.1 | 43.3 |
| Review 4B | 90.7 | 91.1 | 88.6 | 72.7 | **52.2** |

## 5. Findings

1. **Self-refinement can be trained.** Teaching the model to review its own two attempts significantly improves over the base model at both 2B and 4B.
2. **It beats conventional reasoning at 4B.** 75.4% vs 71.6% for CoT fine-tuning on the same problems, statistically significant. At 2B the gap is in the same direction but not significant.
3. **The model really reconsiders.** Its final answer is better than its own first attempt (+7.2 points at 4B), it fixes far more answers than it breaks (50 vs 14 at 4B), and it picks the right attempt 83% of the time.
4. **Reviewing works, rewriting does not.** The Refine ablation, which rewrites the whole solution instead of writing a review, is worse after reconsidering than before (-2.2 points).
5. **A better teacher helps.** Reviews from Qwen3.8-27B point to the exact wrong step more often than reviews from Qwen3.5-9B, and the trained model improves (59.8% to 61.2%), though this difference alone is not significant.
6. **The gains are largest on the hardest problems.** Level 5: 52.2% (Review) vs 43.3% (CoT) vs 38.1% (base) at 4B.
7. **Bigger models reconsider better.** Self-correction gain grows from +3.8 (2B) to +7.2 (4B), and correct picks from 77% to 83%.

## 6. Inference and live demo

The trained models are served in a ChatGPT-style website. A user picks a model, asks a question and watches the answer stream in. For self-refining models, Attempt 1, Attempt 2 and the Review sit in a collapsible "Reasoning" block above the final answer. **Compare mode** sends one question to Base, CoT and Self-refine 4B side by side, which shows the difference between conventional and self-refining reasoning directly.

```
Browser  ->  Vercel (Next.js website)       adds the secret key, picks the server that has the model
         ->  ngrok (fixed public address)
         ->  Kaggle notebook 09 (2x T4)     small FastAPI router: checks the key, builds the prompt, grades the answer
         ->  vLLM                           one model per GPU, streams the text back token by token
```

| Kaggle account | GPU 0 | GPU 1 |
|---|---|---|
| A | Self-refine 4B | CoT 4B |
| B | Base 4B | Self-refine 2B (27B teacher) |

- **Same settings as the evaluation:** the same prompts as notebooks 01 and 07, greedy decoding, `repetition_penalty=1.1`, fp16, up to 3072 new tokens. The website grades the example questions with the same `math_verify` rule.
- **Each adapter is merged into its base model before serving**, exactly as in notebook 07. vLLM can also apply LoRA adapters on top of one base model, which would serve all 8 models, but with vLLM 0.32 it loaded these Qwen3.5 adapters without an error and then ignored them: the fine-tuned models answered like the base model. Merged, Self-refine 4B and CoT 4B gave the **same final answer as the evaluation on 12 of 12** test problems. This is why 4 models are live (one per GPU) and the other 4 appear greyed out.
- **Two Kaggle accounts** give 4 GPUs, so compare mode runs on three GPUs at once.
- **Speed on a T4:** about 15 tokens/s per answer; a self-refine answer (~700 to 1,400 tokens) takes 50 to 100 seconds. Text starts appearing within a second.
- **Each message is answered on its own.** The models were trained on single questions, so chat history is not sent to them.
- **Security:** the API key lives only in Kaggle and Vercel settings; the browser never sees it or the server addresses (checked on the deployed site). Requests without the key are refused.

**Testing:**

| Tests | What they check |
|---|---|
| Unit tests (`app/frontend/tests`) | Splitting answers into sections and clean streaming (no half-written LaTeX on screen), replayed on 20,000+ in-between states of real evaluation outputs |
| Browser tests (`app/frontend/e2e`) | 18 end-to-end tests against mock servers: streaming, grading, compare mode, stop, history, servers going offline, wrong key, phone layout, keyboard use |
| Router tests (`app/kaggle/tests`) | Prompts and decoding match notebooks 01 and 07; grading reproduces every accuracy in section 4 |
| Live check (`app/kaggle/live-check.mjs`) | Asks every live model a MATH-500 problem through the real servers or the deployed website and checks format, final answer and grade |

## 7. Limitations

- **Compute cost.** The review model writes two attempts plus a review, about 2.3x more tokens than CoT. Majority voting over 4 samples of the 4B base model reaches 72.8%; Review 4B is ahead (75.4%) but that difference is not significant (p = 0.19).
- **One benchmark.** All results are on MATH-500 (competition math). Other domains were not tested.
- **The 4B CoT win is close to the threshold** (p = 0.048); a different random seed could move it either way.
- **The teacher sees the correct answer** while writing reviews. This is standard for training data, but the reviews are therefore better informed than anything the student can write at test time.
- **The demo is not always on.** It uses free Kaggle GPUs (about 30 GPU hours a week per account, at most 12 hours per run), so the servers are started for demos.

## 8. Project history

1. **v1 (archived in `archive_v1_phi2/`):** Phi-2 trained for CoT and DCoT (multiple chains). Generations never stopped. Root cause found later: the training examples never ended with an end-of-text token, so the model never learned to stop. Every example in v2 ends with exactly one EOS token.
2. **v2, 2B:** rebuilt from scratch on Qwen3.5-2B-Base with the model's own attempts. First evaluation showed looping outputs; adding `repetition_penalty=1.1` fixed most of them.
3. **Teacher upgrade:** replaced the 9B teacher with Qwen3.8-27B (4-bit) and retrained the review model.
4. **Scaling to 4B:** repeated the full pipeline with Qwen3.5-4B-Base, including its own attempts, reviews, and both Review and CoT training.
5. **Inference:** served the models on Kaggle behind a chat website on Vercel.

## 10. Running it

**Research pipeline:** run notebooks 01, 02, 04/04b, 06 and 07 on Kaggle (GPU T4 x2, internet on); 03, 05 and 08 run on a laptop. For the 4B model set `model_name='Qwen/Qwen3.5-4B-Base'` and `model_tag='qwen4b'` (and `train_dtype=torch.float16` in 06). Main packages: `transformers==5.18.0`, `peft==0.21.1`, `trl==1.14.1`, `vllm`, `math-verify`, `datasets`.

**Live demo** (from the repo root, PowerShell; needs `kaggle.json` and `app/kaggle/accounts.local.json`, which hold the keys and are not in git, see `app/kaggle/accounts.example.json`):

```powershell
.\app\kaggle\push.ps1 -Hours 4          # start notebook 09 on both Kaggle accounts, ready in about 20 minutes
.\app\kaggle\push.ps1 status            # both servers should say "online"
node app/kaggle/live-check.mjs --site https://finetuning-ochre.vercel.app   # end-to-end check
```

The website is deployed on Vercel from `app/frontend` with three settings: `BACKEND_URL_A`, `BACKEND_URL_B` (the two ngrok addresses) and `APP_API_KEY`.

**Website on a laptop without a GPU** (mock servers replay real evaluation outputs), from `app/frontend`: `npm install`, then `node scripts/mock-backend.mjs 9000 4b`, `node scripts/mock-backend.mjs 9001 2b` and `npm run dev`. Tests: `npm test` and `npm run test:e2e`.

**Model weights:** the LoRA adapters are not stored in git (size). They are kept locally under `models/` and in a private Kaggle dataset used by notebook 09.
